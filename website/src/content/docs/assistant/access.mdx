Every tool has an access level. `assistant.access` says the highest level the assistant may use, per integration.

| Level | What it allows | Asks you? |
|---|---|---|
| `none` | Nothing from this integration. Its tools aren't offered. | |
| `read` | Tools that look. | No |
| `write` | Also tools that add something, like saving a link. | Always |
| `control` | Also tools that change or remove something. | Always |

Each level includes the ones before it. `write` and `control` differ only in what you grant: both ask. See [below](#write-and-control).

## Setting it

```yaml title="config.yaml"
assistant:
  model: qwen3:8b
  access:
    default: read
    downloads: control
    docs: write
    cameras: none
```

The keys are your **instance names**, the ones under `integrations:`, not the types. Two qBittorrent instances can have different levels. Valet reports a key that matches no instance as a config problem.

`default` covers every instance you don't name. If `access` is left out, it's `{ default: read }`.

Two other keys are special:

- `config` turns on [editing the config](/assistant/limits/#editing-the-config). Without it, those tools don't exist.
- `valet` is Valet's own tools: reminders, rules, the timeline, the activity log. It defaults to `control`, so reminders and [rules](/assistant/rules/) work with no setup. Each one still asks. `valet: write` keeps reminders and turns rules off, including ones already set up.

## One tool at a time

A key with a dot names one tool: the instance, then the tool's name as its integration's page lists it. It wins over the instance's level, up or down.

```yaml title="config.yaml"
assistant:
  access:
    plex: read
    plex.plex_stop_stream: control   # this one tool may act; the rest of Plex only looks
    downloads.torrent_control: none  # the rest of qBittorrent keeps its level
    valet.report_issue: none         # Valet's own tools too, and the built-ins: valet.plan, valet.show, valet.present, valet.search_everything, valet.web_search, valet.web_read
```

It uses the same levels, and a tool that acts still asks first. `none` takes the tool away everywhere: from the chat, the palette's commands, rules, plans, pins and live cards. A read-only page still caps it at `read`. Valet reports a dotted key that names no tool as a config problem, with the list of tools that instance has.

Dotted keys are optional. Without them, every tool gets its instance's level, as before. They're also a way to [keep the assistant's context small](/assistant/models/#keeping-the-context-small).

## Commands

The palette's plain [commands](/concepts/layout/#the-palette) ("stop plex") follow the same levels, with no model. A command that uses a `control` tool on Plex needs `plex: control`, and still shows its approval card. With no `assistant` block, commands use only tools that look, plus the page's own actions.

## Profiles only narrow

Someone with a [profile](/start/people/) gets an assistant of their own: for each integration and tool, the lower of `assistant.access` and the profile's `access`. Their `default` covers the integrations on their tabs, and Valet's own tools (setup, rules, reminders, the log, plans, pins) and MCP servers aren't theirs. With `approve: owner`, what would ask them asks an owner instead.

## Read-only pages win

Sign-in decides whether Valet may act at all. With `auth.mode: none` and no `auth.trustNetwork`, the assistant is capped at `read`, whatever `assistant.access` says. The same goes for MCP servers. See [sign-in and network safety](/start/sign-in/).

## Write and control

Any tool that isn't `read` stops at an [approval card](/assistant/approvals/) and runs only after you press the button. That covers saving a link, filing a document, adding a to-do, setting or cancelling a reminder, and setting up a rule.

So the two levels don't change how it asks. They change what you're granting: `write` lets the assistant add things, and `control` also lets it change or remove them.

A web page that says "save this" can make the model ask, and nothing more.

## What goes where

Each integration's page lists its tools with their levels. Some examples:

| Level | Examples |
|---|---|
| `read` | [Docker](/integrations/docker/) status and logs, [Immich](/integrations/immich/) search, [Paperless](/integrations/paperless/) search |
| `write` | [Karakeep](/integrations/karakeep/) bookmarks, [Paperless](/integrations/paperless/) filing, [to-do list](/integrations/todo/), [Speedtest Tracker](/integrations/speedtest-tracker/) running a test |
| `control` | [qBittorrent](/integrations/qbittorrent/) pause and remove, [Seerr](/integrations/seerr/) requests, [Plex (Tautulli)](/integrations/tautulli/), [Jellyfin](/integrations/jellyfin/) and [Emby](/integrations/emby/) stopping a stream, [Pi-hole](/integrations/pihole/) pause, [Proxmox](/integrations/proxmox/) starting, shutting down or rebooting a guest |

Every integration written with `service()` has one tool, and it's `read`. The check that runs on them fails any tool that isn't.

## A lower level on the service itself

Access levels limit what Valet offers. They can't limit what a key allows. If you give Valet an admin key, a bug or a bad plugin could use all of it.

So give each service the narrowest key it has. See [give it as little as possible](/security/#give-it-as-little-as-possible).
