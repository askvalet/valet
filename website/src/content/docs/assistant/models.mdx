The `assistant` block picks the model. Leave the block out and there's no assistant.

Two providers are built in: `openai-compatible`, the default, and `anthropic`. The first covers anything that speaks the OpenAI chat API: Ollama, llama.cpp, vLLM, LM Studio, OpenRouter, OpenAI.

The model needs to support tool calling. Without it, the assistant can't read anything.

## Local, through Ollama

```yaml title="config.yaml"
assistant:
  name: Valet
  baseURL: http://ollama:11434/v1
  model: qwen3:8b
```

If you leave out `baseURL`, it defaults to `http://localhost:11434/v1`. Inside the container, `localhost` is the container itself. So set `baseURL` to wherever Ollama really is, such as the Compose service name.

Nothing leaves your network with this setup. The model runs on your hardware, and Valet talks to it directly.

## Other OpenAI-compatible servers

```yaml title="config.yaml"
assistant:
  baseURL: http://llama:8080/v1
  apiKey: ${LLAMA_KEY}        # only if the server wants one
  model: local-model
```

A hosted one looks the same, with its own `baseURL`, `apiKey` and `model`.

## Anthropic

```yaml title="config.yaml"
assistant:
  provider: anthropic
  apiKey: ${ANTHROPIC_API_KEY}
  model: your-model-name
```

`baseURL` is optional here.

## What a hosted model sees

A hosted model sees what the tools return: card data, document text if you let it read documents, and logs if you let it read logs. Keys don't go to it. Valet [redacts](/security/secrets/) them first, but it can only redact values that came from a `${NAME}` in your config. Everything else in a log or a document goes as it is.

If that matters to you, use a local model, or set sensitive integrations to `none`.

## Options

| Option | Default | What it does |
|---|---|---|
| `provider` | `openai-compatible` | `openai-compatible` or `anthropic`. |
| `baseURL` | `http://localhost:11434/v1` for `openai-compatible` | Where the server is. |
| `apiKey` | none | Use `${NAME}`. |
| `model` | required | The model's name on that server. |
| `name` | `Assistant` | What it's called on the page. |
| `instructions` | none | Extra text for the system prompt. |
| `access` | `{ default: read }` | What it may use. See [access levels](/assistant/access/). |
| `maxSteps` | `6` | Tool rounds per answer, 1 to 20. The last step is kept for answering. |
| `reasoning` | `auto` | How much the model thinks before it answers in the chat: `auto` (as the model and its server decide), `off`, `low`, `medium` or `high`. See [thinking](#thinking). |
| `options` | none | Sampling, passed to the model as is: `temperature` (0 to 2), `topP` (above 0, up to 1) and `maxOutputTokens` (64 to 200,000). Leave it out for the server's defaults. |
| `tools` | `all` | `all` sends every tool with every request. `lazy` sends Valet's own tools and a line per integration, and loads an integration's tools when a question needs them: a much smaller prompt on a big setup, for one more step. `auto` is `lazy` once the tools add up to about 6k tokens. |
| `contextWindow` | known Claude models, or what your server reports | How many tokens the model holds, for the chat's context meter and for keeping long chats inside it. |
| `compact` | `true` | Near a known window, summarise the oldest part of a long chat for the model. `false` sends the last 24 messages instead. |
| `models` | none | More models to switch to in the chat, and `auto` for everything the server lists. See [more than one model](#more-than-one-model). |
| `background` | see below | What it does on its own. |
| `suggestions` | four questions | Offered on an empty chat and in the palette. |

A small pie beside the model's name in the chat shows how full its context is, from the tokens the model reported for its last step. Hover or tap it for the numbers. Past three quarters it says that Valet summarises the oldest messages when it fills up, and offers a fresh chat, which starts clean and answers faster. Claude models know their window. For other models Valet asks the server's model list, which vLLM, llama.cpp and similar servers answer with the model's context length (`max_model_len`, `context_length`). If yours doesn't say, as Ollama's doesn't, set `contextWindow` to the length your server runs it with (Ollama's `num_ctx`, say), or the meter shows only the tokens used.

The chat window has its own options under [`chat`](/reference/configuration/#chat). Tool results from older turns shrink to a preview, so a long chat doesn't get slower with every turn.

### Thinking

A model that thinks before it answers, like Qwen 3, is slower. `reasoning: off` turns the thinking off. To an OpenAI-compatible server (vLLM, llama.cpp, SGLang) Valet sends `chat_template_kwargs: { enable_thinking: false }`, which Qwen-style chat templates read; a server that doesn't know it ignores it. `low`, `medium` and `high` send `reasoning_effort`, for models and servers that take it, and leave the thinking on. With Anthropic, `off` turns extended thinking off and `low`, `medium` and `high` set its budget.

It applies to the chat. Background calls and the summary of a long chat keep the model's own default. The chat's header has a **Reasoning** menu too (Auto, Off, Low, Medium, High): it sets the level for that chat only, over what the config says for the model, and a new chat starts on Auto again, which is whatever the config says.

```yaml title="config.yaml"
assistant:
  model: qwen3:8b
  reasoning: off
  options: { temperature: 0.6 }
```

Whatever `reasoning` says, the last step, the one kept for answering, doesn't think first and stops after about 400 tokens. A small model made to answer without tools sometimes repeats itself there instead; this keeps that short. Stray tags a model leaves in its answer (`</think>`, `<trans>`) aren't shown.

### Long chats

When the window is known, Valet sizes what it sends before each answer: the instructions, the tools and the conversation stay under about 70% of the window, leaving room for lookups and the reply. A chat that fits goes as it is. One that doesn't has its oldest turns replaced by a short summary, written by the same model in a separate call with no tools. Your latest question and the turn it belongs to always go whole. The summary is reused on the next turns and extended when the chat grows again.

The chat shows a quiet line where that happened, "Earlier messages summarised to make room". The page keeps the whole conversation; only what's sent to the model gets shorter. Within one answer, results from earlier lookups shrink when they pile up, so a single question can't fill the window either.

If the summary can't be written, or the window isn't known, the oldest messages are left out instead (the last 24 go), and the model is told that earlier turns are missing. If the model's server still says the request is too long, Valet sends it once more with only your latest question and a summary, and if that fails too, the chat says so in plain words instead of showing an error.

## Keeping the context small

Every integration you connect adds its tools to every message the assistant sends, whether the question is about it or not. On a busy homelab with about 90 tools, the first step of a chat is about 16,000 tokens, and about 90% of that is tool definitions. A small local model reads all of it before it starts, so a smaller first step answers sooner. What helped, and what didn't, in testing against a local model:

- **Turn off what you never ask about.** Set `access: none` for integrations you never ask the assistant about (their cards stay on the page), or `read` where you only ask. Use [per-tool access](/assistant/access/#one-tool-at-a-time) to drop single tools. In testing this cut about 10% of tokens with no loss in answers.
- **Connected a lot of integrations and running out of context? Set `tools: lazy` (or `auto`).** The assistant starts with Valet's own tools and a list of what's connected, and loads an integration's tools when a question needs them. In testing this cut prompt tokens per answer by a third on a ~90-tool setup and nearly half on a ~120-tool setup with the same pass rate, but questions about an integration take one extra step (about 2s slower on a fast GPU), so `all` stays the default.
- **Don't connect the same thing twice.** If you connect an [MCP server](/assistant/mcp/) that overlaps a built-in integration, such as Home Assistant's MCP server alongside the Home Assistant integration, turn one of them off.
- **Leave `maxSteps` and `contextWindow` at their defaults.** Lowering them made answers worse: a 32k window or 4 steps dropped pass rates.
- **Keep `reasoning: auto` unless speed matters more.** `reasoning: off` is about 2 to 3 times faster, but the model starts answering follow-up questions without checking, and makes up values.

## More than one model

`assistant.models` lists other models the chat can use. With it, the model's name in the chat's header becomes a menu. The choice holds for that chat, and a new chat starts on the main model again.

```yaml title="config.yaml"
assistant:
  baseURL: http://ollama:11434/v1
  model: qwen3:8b                  # the default, and what background calls use
  models:
    - name: Claude
      provider: anthropic
      model: claude-sonnet-5-5
      apiKey: ${ANTHROPIC_API_KEY}
    - model: qwen3:32b             # same server, a bigger model
      reasoning: off
```

Only `model` is required. An entry can also set `name` (what the menu shows; the model id if left out), `provider`, `baseURL`, `apiKey`, `contextWindow`, `reasoning` and `options`. What it leaves out comes from the main settings, with three exceptions: `baseURL` carries over only to the same provider, `apiKey` only to the same server, so a key never goes to a host it wasn't written for, and `contextWindow` is each model's own. Access, tools, steps and instructions are the same for every choice.

The page only ever sends the name of a choice. The server checks it against this list and refuses anything else, so nobody can point the chat at a model or server you didn't configure. The context meter and long-chat summaries follow the chosen model's window. Background calls (the brief, shared causes, suggested questions, rules) always use the main model. `config check` names duplicate names and an Anthropic entry without a key.

### Everything the server offers

A server with many models (Ollama, llama.cpp, vLLM, LM Studio, a router like LiteLLM or OpenRouter) lists them at `GET /models`. Add `auto` to `models` and the chat offers all of them, after the ones you named:

```yaml title="config.yaml"
assistant:
  baseURL: http://router:4000/v1
  model: qwen3.8-27b
  models:
    - { name: "Fast", model: some-small-model }
    - { name: "Deep", model: big-reasoning-model, reasoning: high }
    - auto        # everything else the server lists, searchable
```

`models: auto` on its own is the same as a list with only `auto` in it. Valet asks the main server (`baseURL`, with its `apiKey`) from its own side, so the key never reaches the browser, and keeps the list for five minutes; the menu has a **Refresh the list** row to ask again. A model found this way is on the main server, so it uses the main settings, with its own window when the list gives one (`max_model_len`, `context_length` and the like) and none otherwise. Models you named, and the main model, aren't listed twice.

Past eight choices the menu becomes a list you can type into: the models you named first, then the ones you picked lately in this browser, then the rest, narrowed as you type (arrows and Enter pick, Esc closes). It shows a hundred matches at a time, so a router with hundreds of models stays quick. If the server doesn't answer, the menu says so and keeps the models you named.

The server still decides: a chat can name the main model, one you named, or one in the latest list (asked again once if it isn't there), and nothing else. A server address or key in a request is never read. Only an OpenAI-compatible server is asked; with `provider: anthropic`, `auto` adds nothing and `config check` says so.

## Background use

Some features call the model without being asked. They get no tools, so they can only say something.

| Option | Default | What it does |
|---|---|---|
| `background.watch` | `true` | When two or more things are wrong at once, asks whether one cause explains them. |
| `background.brief` | `true` | A short summary, shown when you hover the status sentence. Rewritten every half hour while the page is in use, or within five minutes when what's wrong changes. |
| `background.suggest` | `true` | Questions worth asking right now. |
| `background.perDay` | `100` | The most background calls a day, from 1 to 500. |

Calls go one at a time, so a single GPU isn't asked to do two things at once. Rules decide when a call is worth making: one problem on its own never reaches the model. To stop them all, set the first three to `false`.

## Handing the chat to another agent

`assistant.agent` sends the chat to another agent with an OpenAI-compatible API, such as Hermes.

```yaml title="config.yaml"
assistant:
  model: qwen3:8b
  agent:
    name: Hermes
    baseURL: http://hermes:8000/v1
    apiKey: ${HERMES_KEY}
    model: hermes
```

:::caution[Access rules don't apply]
The agent gets the conversation and nothing else from Valet: no tools, no keys, no data. But it runs its own tools, and Valet can't see or stop them. Access levels and approvals protect Valet's assistant, not this one.
:::

The chat says so at the top. Answers are plain text, with no cards. A [read-only page](/start/sign-in/) stays on Valet's own assistant, because the agent can act and that page may only look.
