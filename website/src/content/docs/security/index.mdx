Valet talks to many of your services, so it holds keys to them. This page says what it does with them, how it limits the damage if something goes wrong, and how to give it as little power as possible.

Valet is locked down by default. Each protection below also says what it doesn't cover.

## What it protects

- The keys to your services.
- Your services themselves, from a page, a model, or a stranger on your network.
- What's in them: documents, photos, logs.

## What it assumes

- You control the machine, `config.yaml`, `.env` and the data folder.
- You run plugins you trust. They aren't sandboxed.
- Anyone who can reach an unauthenticated Valet can see the page. That's why you shouldn't put one on the internet.

## Your keys

- **They stay on the server.** Keys live in `.env` or in secret files, and `config.yaml` refers to them as `${NAME}`. Only Valet's server talks to your services. The page gets finished cards. See [secrets](/security/secrets/).
- **They're scrubbed from what leaves.** Every secret a `${NAME}` stood for is redacted from widget errors, live updates, action errors and assistant tool results, in case a service echoes one back. Names that end in `_USER`, `_URL`, `_HOST` or `_PORT` aren't treated as secrets: see [the redactor](/security/secrets/#the-redactor).
- **The assistant never sees them.** It calls tools, and the server makes the requests.
- **What it keeps stays in the data folder.** History, the timeline, the activity log, pins, reminders and cached icons, with secrets redacted from the log. Chat attachments are kept for a day, and never served back out. Sign-in accounts are scrypt hashes.

## What the page may do

- **Read-only unless you say otherwise.** With sign-in off, the default, Valet only shows things. Card buttons and controls are off, and the assistant gets tools that look. It can change things only when `auth.mode` is `local`, `oidc` or `proxy`, or when you set `auth.trustNetwork: true` because the network is the lock. See [sign-in and network safety](/start/sign-in/).
- **Anything that changes something must come from Valet's own origin.** A POST whose `Origin` doesn't match the host is refused.
- **Pictures come through a checked proxy.** See [the image proxy](/security/image-proxy/).
- **The page runs only Valet's scripts.** See [CSP](/security/csp/).
- **It answers only to names it knows.** See [allowed hosts](/security/hosts/).
- **A sandbox keeps Valet's own state apart, nothing more.** With `sandbox: true` nothing is saved, each visitor gets a private copy of the site in memory, and there are no file uploads, config tools or MCP server. Integrations still reach whatever they're pointed at, so on a page that may act, a visitor's press reaches the real service. Use it with made-up services. See [the recipe](/recipes/#a-public-demo).
- **A paired wall display reads the wall, and only the wall.** See [below](#a-paired-wall-display).
- **Searching from ⌘K goes through the chat's doors.** `/api/search` needs a session, uses only tools that look, leaves out any integration or tool that `assistant.access` gives `none`, and passes every answer through the redactor. A row opens only an `http(s)` address. No model sees what you type there.
- **Icons, the wallpaper and your own CSS and font are open.** `/api/icon/`, `/api/wallpaper/`, `/api/custom.css` and `/api/font` answer without sign-in, because the sign-in screen uses them (`/api/favicon/` needs a session). Icons fetch from an outside service. See [requests Valet makes on its own](#requests-valet-makes-on-its-own). If you don't want that, keep Valet behind your own network or proxy.

## Notifications and the app

[Valet as an app](/start/app/) adds a service worker and Valet's own push notifications.

- **The service worker keeps one page.** It caches only the "Valet can't be reached" page. The page itself, its data and anything behind sign-in always come from the server, so an update shows on the next load and a signed-out visitor never sees what someone else saw. It never touches `/api/`.
- **Voice goes where the chat goes.** `/api/voice/transcribe` and `/api/voice/speak` need a session like the chat, are off in the demo, and hand the speech server's address and key to no one. Recordings aren't stored. See [Voice](/assistant/voice/#privacy-and-limits).
- **Turning notifications on is acting.** `/api/push` needs a session from Valet's own origin, like a button, and a read-only page or a demo refuses it. Each browser is one subscription, kept with the account that turned it on. Only that account can turn it off, signing out from ⌘K turns it off, and **Sign out everywhere** turns off every device of that account.
- **The push service can't read them.** Each notification is encrypted for one browser (RFC 8291), and signed with Valet's own key (RFC 8292), so Google, Apple, Mozilla or Microsoft carry it without reading it. They do see when one is sent, how big it is, and that it came from your server. Secrets are redacted from the words first, as everywhere.
- **Valet only posts to real push services.** A subscription is a URL that Valet will post to, so it must be on Google's, Apple's, Mozilla's or Microsoft's push service (`notify.webPush.services`), over HTTPS. It can't point Valet at something on your network.
- **What it keeps is the owner's alone.** The signing key is `data/vapid.json` and the subscriptions are `data/push.json`, both readable only by Valet's user. A subscription the browser drops (the push service answers 404 or 410) is deleted.

## A paired wall display

A [wall display](/concepts/wall/) that can't sign in can be paired with `wall.token`. Off unless you set one, and only with sign-in on.

- **Pairing needs the token.** `/wall#key=…` sends it once, from Valet's own origin. The part after `#` never reaches your proxy's logs. A wrong key slows down per address, as a wrong password does.
- **The cookie is a signature, not the token.** It's HttpOnly, `SameSite=Strict`, and signed with Valet's secret for this purpose only, so it can't pass for a session. Changing the token unpairs every screen.
- **It reads three things and does nothing.** The wall's page, its live updates and the pictures its cards show right now. The page leaves out the title, the assistant, the other cards and the token. Live updates carry only the wall's cards and the weather, and no notices. Every other route, and anything that isn't a GET, refuses it as it would a stranger.
- **What it doesn't cover.** Whoever holds the tablet can read what's on the wall. Put nothing there you wouldn't leave on a screen in that room.

`npm run test:exposure` pairs a screen and tries every route with it.

## The assistant

- **It reads freely and changes nothing without asking.** See [access levels](/assistant/access/) and [approvals](/assistant/approvals/).
- **What it does unasked can only talk.** The brief, the suggestions and the shared-cause line call the model with no tools at all. They have a daily budget.
- **It can't give itself more power.** Editing the config needs `assistant.access.config`, and each save needs your approval. Approvals are signed by the server, so a request can't claim one. A secret only ever goes to hosts it already goes to. Sign-in, plugins, MCP, allowed hosts, notifications and its own access are off limits, and secrets can't be written.
- **Another agent is its own thing.** If `assistant.agent` hands the chat to another agent, it gets the conversation and nothing else from Valet. But it runs its own tools, so access levels and approvals don't cover it. The chat says so.
- **Reminders can only tell you things.** A reminder sends a message. It can't run a tool.
- **Rules act only as approved, and only as allowed now.** A [rule](/assistant/rules/) is the one thing that acts without a fresh press: you approve it once, on a card written from the card's title and the action tool's own words. It runs exactly one integration tool, never the config, Valet's own tools, plans, pins or MCP, and before each run it's checked again against `assistant.access` and whether Valet may act. Lowering access stops it.
- **Pins only look.** Only `read` tools can be pinned, and no model runs after that.
- **Everything it changes is written down**, in `data/activity.json`, with secrets redacted.

[What it can and can't do](/assistant/limits/) covers prompt injection in full.

## Valet stays in its box

The container never gets the host. Anything from outside comes through a narrow read-only door.

- **Docker is read-only, and it has to be.** Point the integration at a socket proxy with `POST=0`, on a network only Valet shares. Never mount the socket itself. Know what that still reads: the proxy allows GET on `/containers`, which includes each container's environment, so a compromised Valet could read secrets kept there. Logs go to the model, so a hosted model sees them. Restarts aren't offered, because this proxy can't allow them without allowing container creation, which is root on the host.
- **The agent can only look.** `agent/valet-agent.py` is one short file of Python's standard library. It runs on your machines so the container doesn't need access to them. It needs a token, answers only about the services you list, has no way to start or stop anything, and passes nothing unchecked to `journalctl`. Bind it to a private address. A test in the repo enforces that it can't change anything.
- **The container is locked down** in the example compose file: not root, a read-only filesystem, no Linux capabilities, no privilege escalation.

```yaml title="docker-compose.yml"
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
```

- **Dependencies are pinned** in `package-lock.json`. The server is bundled, so the image ships no `node_modules`.

## Plugins

Community integrations run inside Valet with the same access as the built-in ones, including the keys you give them. Their cards are checked against the catalog. Their code isn't sandboxed.

Anyone who can write to `data/integrations/` can run code as Valet. Keep that folder, and the data volume, writable only by you. Plugins are single files, so read them before you install them.

## Requests Valet makes on its own

Self-hosters like to know what leaves the box.

- Your services, as configured.
- The model, if you configured one.
- The speech server, if you configured [voice](/assistant/voice/): a recording or an answer's words, when someone uses the mic or the speaker.
- App icons: `/api/icon/` fetches from `cdn.jsdelivr.net` once and keeps them in `data/icons`. Files you put there win.
- Favicons for links: `/api/favicon/` fetches from `icons.duckduckgo.com`, which tells it the link's hostname, and keeps the result.
- Your notification channels, if any.
- Integrations that use public APIs, when you add them: feeds, weather, GitHub, markets, and so on.

The Docker integration also asks image registries what's newest, to spot updates.

## Give it as little as possible

Each service decides what its keys can do. Use the narrowest kind it offers.

| Service | Least-privilege option |
|---|---|
| Immich | An API key with only read permissions (asset, album, person, memory, timeline) |
| Home Assistant | A separate non-admin user for Valet, and its long-lived token. Expose only the entities you want to Assist for MCP |
| Paperless-ngx | A separate user with view permissions (add "add document" only if you want filing from chat) |
| Pi-hole | An app password (Settings, Web interface/API), not your admin password |
| Uptime Kuma | An API key (Settings, API Keys). It only reads metrics |
| Sonarr, Radarr, Prowlarr, Bazarr | These apps only have full API keys. Keep `assistant.access` at `read` unless you want the assistant to search for a title |
| qBittorrent | Its web login can do everything. Keep `assistant.access` at `read` unless you want pause and resume from chat |
| Seerr | Its API key acts as the admin. Requests from chat ask you first |
| Tautulli | Its API key. Stopping a stream from chat asks you first |
| Karakeep | An API key. It can add bookmarks, and saving from chat asks you first |
| Proxmox VE | An API token with the PVEAuditor role on `/`, to look (with privilege separation on, the token needs the role itself, not only its user). For start, shutdown and reboot from chat, add only VM.PowerMgmt, on just the guests you want (`/vms/<id>`) |
| Speedtest Tracker | A token with only "Read results". Add "Run speedtest" only if you want tests started from chat |
| Syncthing | It has one API key, which can do everything. Keep `assistant.access` at `read` unless you want rescans from chat |
| Backrest | Its users can do everything. Keep `assistant.access` at `read` unless you want backups started from chat |
| Healthchecks.io | The project's read-only API key. Pausing and resuming from chat need the full key |
| Mealie | An API token from a user who isn't an admin. Adding to a shopping list from chat asks you first |
| Tandoor | A token with the `read` scope; add `write` only if you want the shopping list from chat |
| Komga, Kavita | A user who isn't an admin (Kavita's server totals on `status` need one). Nothing from chat changes them |
| Miniflux | An API key. Marking read or starring from chat asks you first |

And the general rules:

- **Don't expose Valet to the internet.** Reach it over a VPN or tailnet, or put a sign-in proxy in front, or turn on `auth.mode: local`. It's a control panel for your home.
- Keep `.env` readable only by you: `chmod 600 .env`. Never commit it. `config.yaml` is safe to share.
- Turn on only the integrations you use, and give the assistant only the access you want it to have.

## Reporting a problem

Please don't open a public issue for a security problem. Use GitHub's private vulnerability reporting on the repository: Security, then Report a vulnerability. You'll get a reply within a few days.

## How this is checked

Every change runs these in CI:

- **Attacked from outside.** `npm run test:exposure` starts the real build in each sign-in mode and tries every route without a session, along with forged cookies, spoofed identity headers and path tricks. A new route is found automatically and has to refuse. Anything open on purpose is listed in that file with its reason.
- **A model that is the attacker's.** `npm run test:hostile` gives Valet a model that does whatever an attacker wants and checks that nothing changes without your approval, and that no secret leaves and no power grows even when every approval is clicked. That includes rules: one that would edit the config or make more rules is refused even approved, and one whose integration's access is lowered stops. `npm run eval:inject` runs poisoned content past your own model, for you to run by hand.
- **Signing in, end to end.** The setup code, a wrong password, cross-site requests, signing out, and that passwords are stored hashed.
- **Dependencies and secrets.** `npm audit` (failing on high and critical), and a secret scan of the whole git history.

Automated checks find what they're written to find. They aren't a security audit, and Valet hasn't had an independent one.
