Valet talks to many of your services, so it holds keys to them. This page says what it does with them, how it limits the damage if something goes wrong, and how to give it as little power as possible.

Valet is locked down by default. Each protection below also says what it doesn't cover.

## What it protects

- The keys to your services.
- Your services themselves, from a page, a model, or a stranger on your network.
- What's in them: documents, photos, logs.

## What it assumes

- You control the machine, `config.yaml`, `.env` and the data folder.
- You run plugins you trust. They aren't sandboxed.
- Anyone who can reach an unauthenticated Valet can see the page. That's why you shouldn't put one on the internet.

## Your keys

- **They stay on the server.** Keys live in `.env`, in secret files, or in Vault or 1Password, and `config.yaml` refers to them as `${NAME}`. Only Valet's server talks to your services. The page gets finished cards. See [secrets](/security/secrets/).
- **They're scrubbed from what leaves.** Every secret a `${NAME}` stood for is redacted from widget errors, live updates, action errors and assistant tool results, in case a service echoes one back. Names that end in `_USER`, `_URL`, `_HOST` or `_PORT` aren't treated as secrets: see [the redactor](/security/secrets/#the-redactor).
- **The assistant never sees them.** It calls tools, and the server makes the requests.
- **What it keeps stays in the data folder.** History, the timeline, the activity log, pins, reminders and cached icons, with secrets redacted from the log. Chat attachments are kept for a day, and never served back out. Sign-in accounts are scrypt hashes.

## What the page may do

- **Read-only unless you say otherwise.** With sign-in off, the default, Valet only shows things. Card buttons and controls are off, and the assistant gets tools that look. It can change things only when `auth.mode` is `local`, `oidc` or `proxy`, or when you set `auth.trustNetwork: true` because the network is the lock. See [sign-in and network safety](/start/sign-in/).
- **Anything that changes something must come from Valet's own origin.** A POST whose `Origin` doesn't match the host is refused.
- **Pictures come through a checked proxy.** See [the image proxy](/security/image-proxy/).
- **The page runs only Valet's scripts.** See [CSP](/security/csp/).
- **It answers only to names it knows.** See [allowed hosts](/security/hosts/).
- **A sandbox keeps Valet's own state apart, nothing more.** With `sandbox: true` nothing is saved, each visitor gets a private copy of the site in memory, and there are no file uploads, config tools or MCP server. Integrations still reach whatever they're pointed at, so on a page that may act, a visitor's press reaches the real service. Use it with made-up services. See [the recipe](/recipes/#a-public-demo).
- **A paired wall display reads the wall, and presses only what you list.** See [below](#a-paired-wall-display).
- **Someone with a profile reaches only what it gives them.** See [below](#people-with-a-profile).
- **An MCP client changes nothing by itself.** `mcpServer` is read-only unless you give an integration `write` or `control`. Then each call that would change something waits on the page for a signed-in person to approve it, in the tool's own words; the approval is for that tool with that exact input, once, and lapses after ten minutes. `/api/asks/:id` needs a session from Valet's own origin, like any button, and what runs is what was asked, never anything the answer says. See [Valet as an MCP server](/assistant/mcp/#letting-it-change-things).
- **A hook's token can only knock.** [`hooks`](/concepts/events/#webhooks-in) are off until you name one. `/hooks/<name>` sits outside `/api`, so it needs no session and checks no origin, and each hook answers only to its own token, at least 32 characters, compared as a digest in constant time. No token, a wrong one, another hook's and a hook that isn't there all get the same `401`, and none is logged, so guessing reveals nothing and can't fill the log. What the token can do: put a notice on the page and the timeline, send a push if that hook has `push: true`, publish a `hook` event, and set off the rules that wait on that hook. What it can't do: read anything, change the config, reach a model, or choose what a rule does, since a rule runs the input approved on its card and hears only the hook's name. Its words are shown as plain text, cut to 200 characters a line, with secrets redacted. The body stops at 16 KB, each hook at `rate` calls a minute (30 by default), and a slow page keeps only the newest notices. The token goes in a header (`Bearer`, Basic's password or `X-Valet-Token`), never the address unless that hook says `query: true`. Treat it as a password for that hook alone. Off in a sandbox.
- **Events only go out.** [`events`](/concepts/events/#events-out) sends what Valet notices to the targets you list, after the redactor. The MQTT client never subscribes, so a broker can't tell Valet anything, and it reads what a broker sends defensively. A webhook target's `secret` signs each body (HMAC-SHA256), so the receiver can tell it came from Valet. Anyone who can read the broker or the receiver learns what's going on at home (which services are down, what's playing, what a hook said), so give a broker a password and keep it on your network.
- **Searching from ⌘K goes through the chat's doors.** `/api/search` needs a session, uses only tools that look, leaves out any integration or tool that `assistant.access` gives `none`, and passes every answer through the redactor. A row opens only an `http(s)` address. No model sees what you type there.
- **Icons, the wallpaper and your own CSS and font are open.** `/api/icon/`, `/api/wallpaper/`, `/api/custom.css` and `/api/font` answer without sign-in, because the sign-in screen uses them (`/api/favicon/` needs a session). Icons fetch from an outside service. See [requests Valet makes on its own](#requests-valet-makes-on-its-own). If you don't want that, keep Valet behind your own network or proxy.

## Notifications and the app

[Valet as an app](/start/app/) adds a service worker and Valet's own push notifications.

- **The service worker keeps one page.** It caches only the "Valet can't be reached" page. The page itself, its data and anything behind sign-in always come from the server, so an update shows on the next load and a signed-out visitor never sees what someone else saw. It never touches `/api/`.
- **Telegram goes where the chat goes.** With `assistant.telegram`, Valet reads a bot's messages by asking Telegram for them, so nothing listens for Telegram. A message from anyone not in `users`, or in a group, is dropped without an answer. What's heard goes through the chat's own handler: the same access, the same approvals (two buttons, in the tool's words), the same redactor and activity log. The bot's token is a secret like any other, and Telegram's servers can read the conversation. See [Telegram](/assistant/telegram/#what-to-know).
- **Voice goes where the chat goes.** `/api/voice/transcribe` and `/api/voice/speak` need a session like the chat, are off in the demo, and hand the speech server's address and key to no one. Recordings aren't stored. See [Voice](/assistant/voice/#privacy-and-limits).
- **Turning notifications on is acting.** `/api/push` needs a session from Valet's own origin, like a button, and a read-only page or a demo refuses it. Each browser is one subscription, kept with the account that turned it on. Only that account can turn it off, signing out from ⌘K turns it off, and **Sign out everywhere** turns off every device of that account.
- **The push service can't read them.** Each notification is encrypted for one browser (RFC 8291), and signed with Valet's own key (RFC 8292), so Google, Apple, Mozilla or Microsoft carry it without reading it. They do see when one is sent, how big it is, and that it came from your server. Secrets are redacted from the words first, as everywhere.
- **Valet only posts to real push services.** A subscription is a URL that Valet will post to, so it must be on Google's, Apple's, Mozilla's or Microsoft's push service (`notify.webPush.services`), over HTTPS. It can't point Valet at something on your network.
- **What it keeps is the owner's alone.** The signing key is `data/vapid.json` and the subscriptions are `data/push.json`, both readable only by Valet's user. A subscription the browser drops (the push service answers 404 or 410) is deleted.

## A paired wall display

A [wall display](/concepts/wall/) that can't sign in can be paired with `wall.token` (or a screen's own `token`). Off unless you set one, and only with sign-in on.

- **Pairing needs the token.** `/wall#key=…` sends it once, from Valet's own origin. The part after `#` never reaches your proxy's logs. A wrong key slows down per address, as a wrong password does.
- **The cookie is a signature, not the token.** It's HttpOnly, `SameSite=Strict`, and signed with Valet's secret for this purpose only, so it can't pass for a session. Changing the token unpairs every screen.
- **It reads three things.** The page of its screen, its live updates and the pictures its cards show right now. The page leaves out the title, the assistant, the other cards, the other screens, every token, `people` and every page's `when`. Live updates carry only its pages' cards and the weather, no notices, and which of its pages may show now. Who is home is judged on the server and never sent; a card that a `when` reads but no page shows never reaches it.
- **Without `touch`, it presses nothing.** Every route other than those three reads refuses it as it would a stranger.
- **With `touch`, it may press exactly what you list, as the card offers it.** One more route answers it: `POST /api/action/:instance/:action`, and only when a card on its screen's `touch` list, on one of its pages, offers that action right now, with exactly the arguments the card gives it, plus the one value that control takes (on or off for a switch, a number within a slider's or the thermostat's range, one of a choice's options). So a wall that may switch a lamp can't reach the lock behind the same action, an action on another instance or another card, an argument the card doesn't give, or a value out of range. Then the action's own input check runs, as it does for a person. Presses still need Valet's own origin, are limited to 30 a minute per token, and each is in the activity log as **Wall display** (with the screen's name). A read-only Valet gives a wall nothing to press. Chat, commands, search, approvals, pins, the config and every other route still refuse it.
- **A screen's token is that screen's.** A screen with its own `token` reaches only its own pages and its own `touch` list; one without shares `wall.token`.
- **`hold` is a guard, not a lock.** It makes the tablet ask for a long press, so a brush does nothing; the server can't tell a held press from a quick one. Anything you wouldn't hand to whoever stands at the tablet stays off the list.
- **What it doesn't cover.** Whoever holds the tablet can read what's on the wall and press what's listed, and so can whoever copies its cookie. Put nothing there you wouldn't leave on a screen in that room, and change the token if a tablet goes missing.

`npm run test:exposure` pairs a screen and tries every route with it, then turns touch on and tries an unlisted action, a listed one on another instance, made-up arguments, another screen's token, a forged or missing cookie, another site's origin and too many presses.

## People with a profile

With sign-in on, an account `users` names gets that [profile](/start/people/)'s narrower Valet. An account it doesn't name is an owner, exactly as without profiles.

- **It's held on the server, route by route.** One view of the site is worked out per person, and every route answers from it. A card that isn't on their tabs isn't in their page, their live updates, the image proxy, a command, ⌘K's search, the approval card's words or anything the assistant can draw or search. A picture comes through only if a card of theirs shows it or their assistant may read its integration.
- **It only narrows.** Their assistant's level for each integration and tool is the lower of `assistant.access` and the profile's. Valet's own tools (setup, rules, reminders, the activity log, plans, pins), MCP servers, other models and your chat commands aren't theirs. Page buttons are only the `actions` it lists.
- **Owners' things stay owners'.** The activity log, rules, pins, the year in review, the brief and suggested questions, notifications, notices about Valet's own things, approvals asked from outside the chat, and config errors refuse them or come back empty.
- **`approve: owner` asks an owner.** Their assistant's change waits for an owner on the page, in the tool's own words; a yes covers that exact call from that person, once. They can't answer it themselves: `/api/asks/:id` is for owners only.
- **A typo never widens anything.** A name mapped to a profile that isn't there sees nothing. Names compare without case. If `users` leaves no owner, Valet says so and promotes nobody.
- **The assistant can't change it.** `profiles` and `users` are the owner's to edit by hand, like `auth`.

`npm run test:exposure` signs in with a profile and tries every route, each with a written decision for what someone with a profile gets.

## The assistant

- **It reads freely and changes nothing without asking.** See [access levels](/assistant/access/) and [approvals](/assistant/approvals/).
- **What it does unasked can only talk.** The brief, the suggestions and the shared-cause line call the model with no tools at all. They have a daily budget.
- **It can't give itself more power.** Editing the config needs `assistant.access.config`, and each save needs your approval. Approvals are signed by the server, so a request can't claim one. A secret only ever goes to hosts it already goes to. Sign-in, profiles and `users`, plugins, MCP, allowed hosts, notifications and its own access are off limits, and secrets can't be written.
- **Another agent is its own thing.** If `assistant.agent` hands the chat to another agent, it gets the conversation and nothing else from Valet. But it runs its own tools, so access levels and approvals don't cover it. The chat says so.
- **Reminders can only tell you things.** A reminder sends a message. It can't run a tool.
- **Rules act only as approved, and only as allowed now.** A [rule](/assistant/rules/) is the one thing that acts without a fresh press: you approve it once, on a card written from the card's title and the action tool's own words. It runs exactly one integration tool, never the config, Valet's own tools, plans, pins or MCP, and before each run it's checked again against `assistant.access` and whether Valet may act. Lowering access stops it. One set off by a hook runs the same approved input whatever the caller sent.
- **Web search is off unless you set it, and only looks.** With `assistant.webSearch`, the words of a search go to your provider, and the model is told to keep anything private out of them. Results and pages are a stranger's text: nothing they say can change anything without your press. `web_read` opens only an address a search returned, only on the public internet (every address the name has is checked, the connection goes to the checked one, and each redirect is checked again), with no cookies or keys, and with time, size and type capped. It's never offered to an MCP client. See [web search](/assistant/web-search/).
- **Pins only look.** Only `read` tools can be pinned, and no model runs after that.
- **Everything it changes is written down**, in `data/activity.json`, with secrets redacted.

[What it can and can't do](/assistant/limits/) covers prompt injection in full.

## Valet stays in its box

The container never gets the host. Anything from outside comes through a narrow read-only door.

- **Docker is read-only, and it has to be.** Point the integration at a socket proxy with `POST=0`, on a network only Valet shares. Never mount the socket itself. Know what that still reads: the proxy allows GET on `/containers`, which includes each container's environment, so a compromised Valet could read secrets kept there. Logs go to the model, so a hosted model sees them. Restarts aren't offered, because this proxy can't allow them without allowing container creation, which is root on the host.
- **The agent can only look.** `agent/valet-agent.py` is one file of Python's standard library. It runs on your machines so the container doesn't need access to them. It needs a token (compared in constant time) for everything but "I'm alive", answers only GET, and everything it can report is off until you turn it on there. Bind it to a private address, and `VALET_AGENT_ALLOW` can name the only addresses that may ask. A test in the repo runs it against stand-ins and holds it to this: no way to start, stop or change anything, files only opened to read, Docker only asked with GET, the standard library only. Part by part:
  - **Services** (`VALET_AGENT_UNITS`): `systemctl show` and `journalctl` for the services you list, matched exactly, so nothing typed reaches either command. Up to 2,000 log lines.
  - **The machine** (`VALET_AGENT_METRICS`, `VALET_AGENT_MOUNTS`): files under `/proc`, `/sys` and `/etc/os-release`, read and capped, and the free space of the mounts you list. It runs no program for these.
  - **Containers** (`VALET_AGENT_DOCKER`, `VALET_AGENT_CONTAINERS`): GET only, and only to a fixed list of paths: the container list, one container's numbers, its logs and how it last ended. A container's id comes from Docker's own list, never from the request. Of the container list it passes on the name, state, image and compose project, never the environment, mounts or ports; of how it ended, the exit code, restarts and whether it ran out of memory. Even so, give it a socket proxy with `POST=0` rather than the socket: the socket would need your user in the `docker` group, which is root on that machine.
  - **Logs** leave as plain text: colour codes and control characters out, each line cut at 1,000 characters, at most 2,000 lines. They go to the model, so treat what's in them as data.
- **The container is locked down** in the example compose file: not root, a read-only filesystem, no Linux capabilities, no privilege escalation.

```yaml title="docker-compose.yml"
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
```

- **Dependencies are pinned** in `package-lock.json`. The server is bundled, so the image ships no `node_modules`.

## Plugins

Community integrations run inside Valet with the same access as the built-in ones, including the keys you give them. Their cards are checked against the catalog. Their code isn't sandboxed.

Anyone who can write to `data/integrations/` can run code as Valet. Keep that folder, and the data volume, writable only by you. Plugins are single files, so read them before you install them.

## Requests Valet makes on its own

Self-hosters like to know what leaves the box.

- Your services, as configured.
- The model, if you configured one.
- The speech server, if you configured [voice](/assistant/voice/): a recording or an answer's words, when someone uses the mic or the speaker.
- App icons: `/api/icon/` fetches from `cdn.jsdelivr.net` once and keeps them in `data/icons`. Files you put there win.
- Favicons for links: `/api/favicon/` fetches from `icons.duckduckgo.com`, which tells it the link's hostname, and keeps the result.
- Your notification channels, if any.
- Your search provider, if you configured [web search](/assistant/web-search/): the words the assistant searches for. And the pages it then reads, each asked for with a plain GET.
- Your [event targets](/concepts/events/#events-out), if any: a webhook or an MQTT broker.
- Integrations that use public APIs, when you add them: feeds, weather, GitHub, markets, and so on.

The Docker integration also asks image registries what's newest, to spot updates.

## Give it as little as possible

Each service decides what its keys can do. Use the narrowest kind it offers.

| Service | Least-privilege option |
|---|---|
| Immich | An API key with only read permissions (asset, album, person, memory, timeline) |
| Home Assistant | A separate non-admin user for Valet, and its long-lived token. Expose only the entities you want to Assist for MCP |
| Paperless-ngx | A separate user with view permissions (add "add document" only if you want filing from chat) |
| Pi-hole | An app password (Settings, Web interface/API), not your admin password |
| Uptime Kuma | An API key (Settings, API Keys). It only reads metrics |
| Sonarr, Radarr, Prowlarr, Bazarr | These apps only have full API keys. Keep `assistant.access` at `read` unless you want the assistant to search for a title |
| qBittorrent | Its web login can do everything. Keep `assistant.access` at `read` unless you want pause and resume from chat |
| Seerr | Its API key acts as the admin. Requests from chat ask you first |
| Tautulli | Its API key. Stopping a stream from chat asks you first |
| Karakeep | An API key. It can add bookmarks, and saving from chat asks you first |
| Proxmox VE | An API token with the PVEAuditor role on `/`, to look (with privilege separation on, the token needs the role itself, not only its user). For start, shutdown and reboot from chat, add only VM.PowerMgmt, on just the guests you want (`/vms/<id>`) |
| Speedtest Tracker | A token with only "Read results". Add "Run speedtest" only if you want tests started from chat |
| Syncthing | It has one API key, which can do everything. Keep `assistant.access` at `read` unless you want rescans from chat |
| Backrest | Its users can do everything. Keep `assistant.access` at `read` unless you want backups started from chat |
| Healthchecks.io | The project's read-only API key. Pausing and resuming from chat need the full key |
| Mealie | An API token from a user who isn't an admin. Adding to a shopping list from chat asks you first |
| Tandoor | A token with the `read` scope; add `write` only if you want the shopping list from chat |
| Komga, Kavita | A user who isn't an admin (Kavita's server totals on `status` need one). Nothing from chat changes them |
| Miniflux | An API key. Marking read or starring from chat asks you first |

And the general rules:

- **Don't expose Valet to the internet.** Reach it over a VPN or tailnet, or put a sign-in proxy in front, or turn on `auth.mode: local`. It's a control panel for your home.
- Keep `.env` readable only by you: `chmod 600 .env`. Never commit it. `config.yaml` is safe to share.
- Turn on only the integrations you use, and give the assistant only the access you want it to have.

## Reporting a problem

Please don't open a public issue for a security problem. Use GitHub's private vulnerability reporting on the repository: Security, then Report a vulnerability. You'll get a reply within a few days.

## How this is checked

Every change runs these in CI:

- **Attacked from outside.** `npm run test:exposure` starts the real build in each sign-in mode and tries every route without a session, along with forged cookies, spoofed identity headers and path tricks. A new route is found automatically and has to refuse. Anything open on purpose is listed in that file with its reason.
- **A model that is the attacker's.** `npm run test:hostile` gives Valet a model that does whatever an attacker wants and checks that nothing changes without your approval, and that no secret leaves and no power grows even when every approval is clicked, by you or by someone with a profile. That includes rules: one that would edit the config or make more rules is refused even approved, whether a card or a hook sets it off; one whose integration's access is lowered stops; and one set off by a hook runs what was approved, whatever the hook was sent, with none of it reaching the model. `test:exposure` also attacks `/hooks/<name>` with no token, wrong ones, another hook's, oversized bodies and other methods. `npm run eval:inject` runs poisoned content past your own model, for you to run by hand.
- **Signing in, end to end.** The setup code, a wrong password, cross-site requests, signing out, and that passwords are stored hashed.
- **Dependencies and secrets.** `npm audit` (failing on high and critical), and a secret scan of the whole git history.

Automated checks find what they're written to find. They aren't a security audit, and Valet hasn't had an independent one.
