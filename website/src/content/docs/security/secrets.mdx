Secrets don't go in `config.yaml`. It refers to them, so you can share or commit the file.

## Four ways to refer to a secret

| In `config.yaml` | Where the value comes from |
|---|---|
| `${NAME}` | The environment variable `NAME`. |
| `${NAME}`, with `NAME_FILE` set | The file `NAME_FILE` points at. This is the Docker convention. |
| `${secret:name}` | The file `/run/secrets/name`, for Docker and Kubernetes secrets. |
| `${file:/path}` | Any file. |

Names are capitals, digits and underscores. File values have their surrounding whitespace trimmed, and a file over 64 KB is refused. The environment wins over `NAME_FILE`. `${secret:name}` refuses a name that leads out of `/run/secrets`.

```yaml title="config.yaml"
integrations:
  downloads:
    type: qbittorrent
    url: http://qbittorrent:8080
    username: ${QBIT_USER}
    password: ${secret:qbit_password}
```

A `${NAME}` that isn't set, or a file that can't be read, stops the config from loading with an error that names it and says where Valet looked. Write `\${NAME}` for a literal `${NAME}`.

This works anywhere in the file, not only for keys. An `.env` file holds the values when you use `env_file` in Compose. Keep it private with `chmod 600 .env`.

## Other places a name can come from

A `secrets` block adds three more places a plain `${NAME}` can come from. Nothing else in the file changes.

```yaml title="config.yaml"
secrets:
  files: /run/secrets
  vault:
    url: https://vault.example.com:8200
    token: ${VAULT_TOKEN}
  onepassword:
    url: http://op-connect:8080
    tokenFile: /run/secrets/op_token
    vault: Homelab
  refresh: 1h
```

Valet takes the first of these that has the name:

1. The environment variable `NAME`.
2. The file `NAME_FILE` points at.
3. `secrets.files`: a file called `NAME`, or `name`, in that folder.
4. `secrets.vault`: the key `NAME`, or `name`, in one Vault secret.
5. `secrets.onepassword`: the field labelled `NAME`, or `name`, in one 1Password item.

The environment comes first, so an install that keeps everything in `.env` behaves as before. You only need the parts you use.

### A folder of files

Docker and Kubernetes mount each secret as a file. With `files: /run/secrets`, `${SONARR_KEY}` reads `/run/secrets/SONARR_KEY`, or `/run/secrets/sonarr_key` if that's how you named it.

```yaml title="docker-compose.yml"
services:
  valet:
    secrets: [sonarr_key]
secrets:
  sonarr_key:
    file: ./secrets/sonarr_key
```

A link is followed only while it stays inside the folder, which is how Kubernetes mounts them. One that leads out is refused.

### HashiCorp Vault

Valet reads one secret from a KV version 2 engine. Its keys are the names.

```sh
vault kv put secret/valet SONARR_KEY=... PLEX_TOKEN=...
```

| Option | Default | |
|---|---|---|
| `url` | required | Vault's address, `http` or `https`. |
| `token` or `tokenFile` | required | A token that may read that one secret. |
| `mount` | `secret` | Where the KV engine is mounted. |
| `path` | `valet` | The secret in it. |
| `namespace` | none | For Vault Enterprise and HCP. |

Give Valet a token whose policy allows `read` on `secret/data/valet` and nothing more.

### 1Password Connect

Valet reads one item from a [Connect server](https://developer.1password.com/docs/connect/) you run. The item's field labels are the names. It needs no `op` program, so the container stays as small and read-only as it is.

| Option | Default | |
|---|---|---|
| `url` | required | The Connect server's address. |
| `token` or `tokenFile` | required | A Connect token that may read that vault. |
| `vault` | required | The vault's name or ID. |
| `item` | `Valet` | The item's title or ID. |

1Password is asked only for names Vault didn't have. Neither is asked when the environment and the files have everything.

### The provider's own token

The token that opens Vault or 1Password comes from the environment or a file, and from nowhere else:

- `token: ${VAULT_TOKEN}` reads the environment variable, or the file `VAULT_TOKEN_FILE` points at.
- `tokenFile: /run/secrets/vault_token` reads that file.

Inside the `secrets` block, `${NAME}` never reads `files`, Vault or 1Password. A token typed straight into the file still works, and `config check` reports it as a problem.

### What Valet does with them

- **Only the address you wrote gets the token.** Each provider is a few `GET` requests over `http` or `https`. No redirect is followed. Use `https` unless the provider is on the same machine or a network you trust.
- **A slow or odd answer is dropped.** Valet waits 10 seconds, and reads at most 512 KB.
- **Values stay in memory.** They aren't written to disk or to the log, and they don't reach the browser.
- **They're all redacted**, whatever the variable is called, and so are the providers' tokens.
- **An error names the variable and the provider.** It never has a value or a token in it.
- **The assistant can't see or change the block**, even with `assistant.access.config`. A provider's token can't be put anywhere else in the file by it. A `${NAME}` from a provider is held to the hosts it already goes to, like any other.

### When a provider is down, and when a value changes

Values are read when Valet starts and each time `config.yaml` changes. If a provider can't be reached during a reload, the reload fails whole and the last good config keeps running, as with any broken edit. At startup there is nothing to fall back on, so Valet doesn't start, and the log says which provider and which names.

`refresh: 1h` asks the files and the providers again on a timer, from `1m` to `7d`. The page is rebuilt only when a value changed. A refresh that fails is logged, and the values Valet has stay in use.

## The redactor

Services sometimes echo a key back, in an error message or a URL. So every secret a `${...}` stood for goes on a list, and that list is cut out of what leaves the server. It becomes `•••`.

It runs over:

- Widget errors and live updates.
- Action results and errors.
- Assistant tool results, before the model sees them.
- MCP results.
- The activity log, before it's written.
- The approval card's words.
- Your own CSS, when it's served, and `config print`.

Plain `${NAME}` values whose name ends in `USER`, `USERNAME`, `LOGIN`, `URL`, `HOST`, `HOSTNAME`, `PORT`, `ADDR` or `ADDRESS`, as a whole word (`QBIT_USER`, `PLEX_URL`, not `SUPERUSER`), aren't on the list. They aren't secrets, and blanking one mangles real text: `sam` inside `samantha`. A name that also has `TOKEN`, `KEY`, `SECRET`, `PASS`, `WEBHOOK`, `ICS` or `CAL` in it still counts, and so do the file forms and anything from `secrets.files`, Vault or 1Password.

### Its limits

- It only knows values that came through `${...}`. A key typed straight into `config.yaml` isn't redacted. That's one more reason not to.
- Values under 4 characters are skipped. Values under 8 match only as whole words, so a short password doesn't punch holes in ordinary text.
- It matches the value exactly. If a service base64-encodes or truncates your key, the result won't match.
- Other sensitive things in a document or log, such as a name or an address, aren't secrets to Valet, and pass through.

## Who can see what

| | The browser | The model |
|---|---|---|
| Keys in `${...}` | Never | Never |
| Service URLs | In a card's link, if you set `href`, or the `url` by default | If a tool returns them |
| Card data | Yes | What the tools return |

A card's title links to `href`, or to `url` when there's no `href`. So set `href` when the address Valet uses is internal and you'd like the link to go elsewhere.

## Checking your file

```sh
docker exec valet node dist/server.js config print
```

`config print` shows what Valet made of your config, with secrets redacted. `config check` names every problem. See [the plugin tools](/build/check/) for the rest of the commands.
